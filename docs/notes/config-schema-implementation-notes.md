# Implementation notes: gui configuration provider system

Deviations and clarifications discovered while implementing
`docs/plans/gui-configuration.md`, recorded here so later commits (and
other agents) don't have to rediscover them. The plan doc itself is not
edited in place; it stays the historical high-level design.

## Phase 1 commits 11 and 12 swapped

The plan ordered "add ConfigValues flatten and unflatten" (11) before "add
ConfigPatch and FieldError types" (12). Building `unflatten` surfaced a
real dependency the plan didn't anticipate: converting a `ConfigValue`
back into json can fail (e.g. `ConfigValue::Ref("not a number")` for a
`ChannelRef` field), and that failure has to be reported as a `FieldError`
at the offending path -- not silently coerced to `null`/`0`, which would
turn into a confusing, path-less deserialize failure later in
`with_patch`. So `unflatten` needs `FieldError` to exist first. Executed
order: `ConfigPatch`/`FieldError` (formerly 12) landed as commit 11;
`flatten`/`unflatten` (formerly 11) landed as commit 12. Same content,
titles unchanged, order flipped.

## `FieldKind::Float` added (phase 1, commit 5)

The plan's `ConfigValue` (section 5.2) already had a `Float(f64)` variant,
but `FieldKind` (section 5.3) had no matching variant, which would have
made `Float` unreachable from any real schema. Added `FieldKind::Float {
min, max, step, unit }`, mirroring `Int`. No v1 provider uses it yet, but
`ConfigField for f64` needs a real `FieldKind` to report.

## `config_fields()`/`descriptor()` split on `Configurable` (phase 1, commit 13)

The plan (section 5.5) described a single derived `config_schema()`
method. That doesn't compose: a struct used only as nested `Section` or
`Collection` item content (e.g. the settings inside a `Toggled<T>`) needs
to contribute `Vec<ConfigNode>` to its parent's tree, but has no provider
identity of its own for a `ProviderDescriptor`. Split into `config_fields`
(always generated by the derive) and `descriptor` (only generated when
the container has `#[config(id = ...)]` attributes, i.e. only for a
provider's actual root type; the trait's default `descriptor()` panics,
which is a fair programmer-error signal since such a type was never meant
to be registered with a `ConfigurationProvider`). `config_schema()`
survives as a provided method that just combines the two.

## Collection item removal (phase 1, before commit 14)

The plan never addressed how a patch removes a `Collection` item (e.g.
deleting an autodelete timer for a channel) -- discovered while writing
end-to-end tests for commit 14. `Configurable::with_patch` now treats
setting any path to `ConfigValue::Unset` as removing that path _and
everything nested under it_ from the merged values, not just that one
entry:

- For a scalar field, this clears an `Option<T>` back to `None` (it falls
  through to the field's default, same as never having been set).
- For a `Collection` item's own bare path (e.g. `timers[9001]`, no field
  suffix), this removes the entire item: every path nested under it
  disappears, so `unflatten`'s key scan no longer finds that key at all.

There's no separate "remove" value or a distinct operation on
`ConfigPatch` -- adding an item already works for free (a change to a
path that didn't exist before just gets defaults for its other fields via
`unflatten`'s fallback to `field.default`), so this makes removal the
symmetric inverse of that, using a value (`Unset`) that already existed
rather than growing the value/patch model further.
