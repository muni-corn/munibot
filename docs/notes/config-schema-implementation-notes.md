# Implementation notes: gui configuration provider system

Deviations and clarifications discovered while implementing
`docs/plans/gui-configuration.md`, recorded here so later commits (and
other agents) don't have to rediscover them. The plan doc itself is not
edited in place; it stays the historical high-level design.

## Phase 1 commits 11 and 12 swapped

The plan ordered "add ConfigValues flatten and unflatten" (11) before "add
ConfigPatch and FieldError types" (12). Building `unflatten` surfaced a
real dependency the plan didn't anticipate: converting a `ConfigValue`
back into json can fail (e.g. `ConfigValue::Ref("not a number")` for a
`ChannelRef` field), and that failure has to be reported as a `FieldError`
at the offending path -- not silently coerced to `null`/`0`, which would
turn into a confusing, path-less deserialize failure later in
`with_patch`. So `unflatten` needs `FieldError` to exist first. Executed
order: `ConfigPatch`/`FieldError` (formerly 12) landed as commit 11;
`flatten`/`unflatten` (formerly 11) landed as commit 12. Same content,
titles unchanged, order flipped.

## `FieldKind::Float` added (phase 1, commit 5)

The plan's `ConfigValue` (section 5.2) already had a `Float(f64)` variant,
but `FieldKind` (section 5.3) had no matching variant, which would have
made `Float` unreachable from any real schema. Added `FieldKind::Float {
min, max, step, unit }`, mirroring `Int`. No v1 provider uses it yet, but
`ConfigField for f64` needs a real `FieldKind` to report.

## `config_fields()`/`descriptor()` split on `Configurable` (phase 1, commit 13)

The plan (section 5.5) described a single derived `config_schema()`
method. That doesn't compose: a struct used only as nested `Section` or
`Collection` item content (e.g. the settings inside a `Toggled<T>`) needs
to contribute `Vec<ConfigNode>` to its parent's tree, but has no provider
identity of its own for a `ProviderDescriptor`. Split into `config_fields`
(always generated by the derive) and `descriptor` (only generated when
the container has `#[config(id = ...)]` attributes, i.e. only for a
provider's actual root type; the trait's default `descriptor()` panics,
which is a fair programmer-error signal since such a type was never meant
to be registered with a `ConfigurationProvider`). `config_schema()`
survives as a provided method that just combines the two.

## Collection item removal (phase 1, before commit 14)

The plan never addressed how a patch removes a `Collection` item (e.g.
deleting an autodelete timer for a channel) -- discovered while writing
end-to-end tests for commit 14. `Configurable::with_patch` now treats
setting any path to `ConfigValue::Unset` as removing that path _and
everything nested under it_ from the merged values, not just that one
entry:

- For a scalar field, this clears an `Option<T>` back to `None` (it falls
  through to the field's default, same as never having been set).
- For a `Collection` item's own bare path (e.g. `timers[9001]`, no field
  suffix), this removes the entire item: every path nested under it
  disappears, so `unflatten`'s key scan no longer finds that key at all.

There's no separate "remove" value or a distinct operation on
`ConfigPatch` -- adding an item already works for free (a change to a
path that didn't exist before just gets defaults for its other fields via
`unflatten`'s fallback to `field.default`), so this makes removal the
symmetric inverse of that, using a value (`Unset`) that already existed
rather than growing the value/patch model further.

## Phase 2 (derive macros) scope decisions

Made while designing `munibot_config_derive`, before writing any codegen.
None of these are visible yet in committed code -- recorded here so the
codegen commits that follow don't need to re-litigate them.

**Only three field shapes are recognized**, by name-based syntax matching
(a proc macro sees syntax, not resolved types): `Toggled<T>` becomes a
toggled `Section`, `BTreeMap<K, V>` becomes a `Collection`, and every
other type is assumed to implement `ConfigField` directly (a `Field`).
There is deliberately **no support for a plain, un-toggled nested
`Section`** in v1 -- neither `LoggingConfig` nor `AutoDeleteConfig` needs
one (logging's section is always toggled; autodelete's collection has no
enclosing section at all), and without an explicit opt-in attribute a
plain nested struct field is syntactically indistinguishable from a
`ConfigChoice`-derived enum field (both are just "some other type used
directly"). If a future provider needs an un-toggled section, the clean
extension is an explicit `#[config(section)]` field attribute rather than
trying to guess from the type alone.

**Dropped the `default` field attribute.** `Configurable: Default` is
already a supertrait bound, so a field's schema default can always be
computed as `<FieldType as ConfigField>::to_value(&Self::default().field)`
-- extracted from the struct's own `Default` impl, which is the one place
a provider author should ever need to state a default. A parallel
`#[config(default = ...)]` attribute would just be a second place the
same fact could drift from the first (e.g. `#[derive(Default)]` giving
one answer, a stale attribute giving another). Where a provider wants a
non-derived default (e.g. autodelete's 24-hour lifetime, since
`Duration::default()` is zero), it should implement `Default` by hand
instead of deriving it.

**`min`/`max` are plain numbers, not human-readable duration strings.**
The plan's `AutoDeleteConfig` example (section 6.3) showed
`#[config(min = "1h", default = "24h")]` on a `SettingDuration` field,
implying compile-time `humantime` parsing inside the proc macro. Combined
with dropping `default` above, and to avoid a proc-macro crate needing
`humantime` purely to parse attribute strings at macro-expansion time,
`min`/`max` are plain expressions (see `FieldAttrs` in `attrs.rs`)
interpreted as whatever unit the field's `FieldKind` uses -- seconds for
`SettingDuration`. `#[config(min = 3600)]` instead of `min = "1h"`. A
provider can still name a `const MINIMUM_LIFETIME_SECS: u64 = 3600;` next
to the struct for readability.

**`required` is a schema/display-only hint in v1, with no generated
runtime check.** The obvious real use -- "a log channel is required once
logging is enabled" -- is a _conditional_ requirement (only matters while
a sibling toggle is on), and generating that generally means the derive
would need to understand `Toggled<T>` gating inside `validate()`, not
just inside schema generation. Deferred; a provider that genuinely needs
this can still override `Configurable::validate` by hand (it's a normal
trait method, independent of what the derive generates).

**`visible_when` has no field attribute in v1.** The only case either
real provider needs -- a toggled section's children only mattering while
its toggle is on -- is already covered by `Toggled<T>`'s automatic
wiring. An explicit `#[config(visible_when = "...")]` for arbitrary
cross-field conditions is deferred until a provider actually needs one.

**`ConfigChoice`-derived enums must keep their `Serialize`/`Deserialize`
in sync with their choice ids by construction, not by convention.**
Rather than requiring `#[derive(Serialize, Deserialize)]` plus a matching
`#[serde(rename_all = ...)]` on the enum (two independent derives that
could drift), `#[derive(ConfigChoice)]` generates `Serialize`/
`Deserialize` itself, delegating to `choice_id`/`from_choice_id`. This
was prototyped by hand in phase 1's `munibot_config/tests/end_to_end.rs`
(`CleanupMode`) before committing to generating it.

## Two bugs found writing the derive's own end-to-end test (phase 2, commit 23)

### Constraint errors never aggregated with coercion errors in the same patch

`with_patch` called `unflatten(...)?` before `validate()`, so if _any_
field in a patch had a structural coercion problem (wrong `ConfigValue`
variant for its `FieldKind`), the whole pipeline returned before
`validate()` ever ran -- silently hiding a `min`/`max`/`max_len`
violation on a _different_ field in the same patch. A patch touching one
bad-type field and one out-of-bounds field reported only the first.

Fixed by moving bounds checking into `unflatten` itself:
`config_value_to_json` (`munibot_config/src/flatten.rs`) now calls
`validate_numeric_bounds`/`validate_text_length` for `Int`/`Float`/
`Duration`/`Text` fields, using the bounds already carried on the
schema's own `FieldKind`. This means bounds violations aggregate with
coercion errors in exactly the pass that already aggregates everything
else. `Configurable::validate()` still independently checks the same
bounds (see `generate_field_validation`) for the case where a value is
constructed directly in Rust, never going through a patch at all -- the
two call sites intentionally share the same `munibot_config` helper
functions rather than duplicating the comparison logic, so this is a
second _call site_, not a second _implementation_.

### `#[config(min = ...)]` never reached the schema at all

More fundamental: `<FieldType as ConfigField>::field_kind()` is a
per-_type_ method -- every `SettingDuration` field, from any struct,
reports the identical `FieldKind::Duration { min: None, max: None }`.
A field-specific `#[config(min = 3600)]` attribute had no way to reach
it, so the schema's `FieldKind` never actually carried a field's real
bounds; only the derive's separately-generated `validate()` ever saw the
attribute (via its own, independent `opt_cast_expr`). This is what made
the bug above possible to miss: `generate_field_validation`'s check
worked in isolation, so `constraint_validation.rs`'s tests all passed
despite the schema itself being wrong.

Fixed in `generate_field_node`: it now calls `field_kind()` to get a
type's default `FieldKind`, then overrides `min`/`max`/`max_len` in
place from the field's own attributes before building the `Field`. See
`generate_kind_override`.

Both bugs are exactly the kind of thing an end-to-end test across the
_whole_ pipeline (schema, patch, coercion, validation) is supposed to
catch, and neither showed up in any single commit's own narrower tests
-- worth keeping in mind when tempted to skip the final integration pass
on a future phase.

## Phase 3 lives in `munibot_core::provider`, not `munibot_core::config` (commit 24)

The plan's suggested layout (section 3.10) put the new trait/registry
code under `munibot_core/src/config/*.rs`, alongside `config.rs`. That
collides: `munibot_core::config` already exists and is the file-based
bot `Config`/`DiscordConfig`/`TwitchConfig` (TOML, read once at startup,
re-exported at the crate root) -- a completely different concern from a
`ConfigurationProvider`. Nesting the new system under the same module
name would put `munibot_core::config::Config` (the TOML struct) and
`munibot_core::config::provider::ConfigurationProvider` (the new trait)
side by side under one name, which reads like they're related when
they aren't. Used `munibot_core::provider` instead, matching the
AGENTS.md module convention (`provider.rs` alongside `provider/`) with
the same submodule breakdown the plan described.

## `ConfigurationProvider` has no `descriptor()` method (commit 25)

The plan's trait (section 7) had a `fn descriptor(&self) -> ProviderDescriptor`
method a provider would implement directly. By the time this trait was
actually written, `Configurable::descriptor()` (phase 1, commit 13)
already existed as the single source of a provider's identity, populated
by the derive from the _config struct's own_ `#[config(id = ...)]`
attributes. A second, separately-implemented `descriptor()` on the
provider itself would just be a second place that identity could be
stated, and drift from the first. Dropped it: `DynConfigProvider::descriptor()`
(commit 26) calls `P::Config::descriptor()` directly, so there remains
exactly one place a provider's id/label/scope are declared.

## Testing async provider code without a real database (commit 25)

`ConfigContext.db` is a real `DbPool`
(`bb8::Pool<AsyncDieselConnectionManager<AsyncMysqlConnection>>`), and
`munibot_core`'s only existing db test harness (`TestDb`, in
`tests/common`) needs an actual reachable MySQL instance -- fine for
integration tests, but overkill (and environment-dependent) for unit
tests of provider glue that never touches the database at all, like
`ConfigurationProvider`'s default method bodies or the `DynConfigProvider`
blanket impl.

`bb8::Pool::builder().build_unchecked(manager)` returns immediately
without waiting for a connection (unlike `.build()`, which `establish_pool`
uses and which would hang or fail against a bogus address) -- it only
spawns a background connection attempt. That's safe to construct and
drop as a `ConfigContext.db` in a unit test, as long as the test's
`ConfigurationProvider` never actually calls `.get()` on it. See
`provider::typed::test_support::unconnected_db_pool`. (An earlier
attempt at this used `std::mem::zeroed()` for a fake pool -- do not do
this. `Pool` holds an `Arc` internally, and zero-initializing one is
undefined behavior the instant anything touches it, including dropping
it at the end of the test.)
